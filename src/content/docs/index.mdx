## You don't lack advice. You lack proof.

VPA, Goldilocks, KRR, cloud consoles and in-house scripts all produce lists of things to optimize. The hard part comes next:

- **Which advice should you trust?** Sources use different algorithms and observation windows, and they often disagree.
- **How do you apply it safely?** In a GitOps setup the cluster mirrors Git. A tool that resizes pods inside the cluster creates drift, and Argo CD or Flux either reverts it or has to be told to ignore it.
- **What did the change actually save?** Most tools report *potential* savings. Few measure what happened after the change, and fewer tie that result to the commit that caused it.

GreenKube closes that loop.

## Three results, never mixed

Every change is reported in three dimensions, each with its own units and its own label (*projected* or *measured*):

<CardGrid>
  <Card title="Money" icon="approve-check">
    Allocated cost from OpenCost, a bundled price catalog (AWS, Azure, OVHcloud, Scaleway) or your own rates. The share expected to reach the bill is shown separately, with its realization factor.
  </Card>
  <Card title="CO₂e" icon="star">
    Operational emissions (energy times grid intensity from Electricity Maps, Wattnet or regional defaults) and embodied emissions, side by side with cost on every recommendation.
  </Card>
  <Card title="Released capacity" icon="rocket">
    CPU cores and memory freed, projected and measured. Never converted to money, and the honest result on a fixed-capacity or on-premises cluster where the bill only moves when a node is removed.
  </Card>
</CardGrid>

## Principles

<div class="feature-cards">
  <div class="feature-card">
    <h3>Git is the only write path</h3>
    <p>No admission webhooks, no in-place mutation, no <code>ignoreDifferences</code> drift. Every change is a pull request your team reviews, and a rollback is a pull request too.</p>
  </div>
  <div class="feature-card">
    <h3>Projected is never shown as realized</h3>
    <p>Projected, measured allocated and realized (billed) savings are separate methods, labelled everywhere, and never added together.</p>
  </div>
  <div class="feature-card">
    <h3>Fail closed, explain why</h3>
    <p>When a change cannot be automated safely, GreenKube refuses and says why, with the fix. A signal that cannot be read is reported as unavailable, never counted as a pass.</p>
  </div>
  <div class="feature-card">
    <h3>Neutral by design</h3>
    <p>Every source is a plugin of the same Source SDK, and the evidence travels with the change into the pull request. A source alone never creates a recommendation: GreenKube's own measurement is required.</p>
  </div>
</div>

## Works where your clusters run

GreenKube runs in the cluster it optimizes, **on-premises and on clouds**: AWS, GCP, Azure, OVHcloud, Scaleway, kubeadm, k3s or bare metal. One Helm install deploys the API, the controller, an isolated renderer and PostgreSQL. There is no profile and no feature flag: discovery, previews, delivery, sync tracking and measurement activate themselves when their prerequisites appear, and the **Setup** page lists what is active and the fix for anything missing.

<Aside type="tip" title="On-premises">
  Install [OpenCost](https://www.opencost.io/) next to GreenKube. Without it, configured rates are never trusted for measurement, so cost savings stay unverified on clusters without a bundled price catalog. Released capacity is measured either way.
</Aside>

## Try it

```bash
# The demo: the full dashboard with sample data, no cluster needed
docker run --rm -p 9000:9000 greenkube/greenkube:0.4.0 demo --no-browser --port 9000
# Open http://localhost:9000
```

```bash
# Install GreenKube 0.4.0 in your cluster
helm repo add greenkube https://GreenKubeCloud.github.io/GreenKube && helm repo update
helm install greenkube greenkube/greenkube -n greenkube --create-namespace --version 0.4.0
```

You can also explore the hosted demo at [demo.greenkube.cloud](https://demo.greenkube.cloud).
