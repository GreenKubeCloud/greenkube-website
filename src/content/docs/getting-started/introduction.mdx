## What is GreenKube?

**GreenKube is an open-source optimization loop for Kubernetes clusters run with GitOps.** It collects optimization recommendations from the tools you already run, ranks them by value and risk, delivers the best ones as reviewable pull requests to your GitOps repository, and then measures what each merged change actually saved: in money, in CO₂e, and in released capacity (CPU cores and memory freed).

```text
 sources ─► recommendation ─► plan (diff + digest) ─► pull request ─► merge
    ▲                                                                   │
    │                                                         Argo CD / Flux sync
    │                                                                   │
 ledger ◄── measurement vs counterfactual ◄── apply detection ◄─────────┘
```

## The problem

Teams running Kubernetes do not lack optimization advice. The hard part comes after the advice:

- **Trust.** VPA, Goldilocks, KRR and cloud recommenders use different algorithms and windows, and they disagree. Which one is right for this workload?
- **Safe application.** With GitOps, the cluster mirrors Git. Resizing pods in place creates drift that Argo CD or Flux reverts, or that has to be hidden with `ignoreDifferences`.
- **Proof.** Most tools stop at *potential* savings. Few measure what happened after the change, and fewer link the result to the commit that caused it.

## How GreenKube answers it

| Stage | What GreenKube does |
|---|---|
| **Aggregate** | Starts from GreenKube's own measurements and reads the other sources of advice in your cluster (VPA and Goldilocks, Robusta KRR reports and anything sent to the push API) into one signal model, provenance kept. |
| **Decide** | GreenKube's measured value decides each size; the other sources raise the confidence when they agree and lower it when they disagree (one vote per engine, contested advice labelled and never approved automatically). A source alone never creates a recommendation. Each recommendation carries evidence, a projected impact, a risk level, a confidence score and a risk-adjusted expected value. |
| **Deliver** | Finds the workload's Git source through Argo CD or Flux, renders the change in an isolated sandbox, and opens a pull request on GitHub, GitLab or Gitea once a signed-in user approves the exact diff (its digest). |
| **Verify** | Waits for Argo CD or Flux to sync the merged revision, then detects that the new configuration is live. |
| **Measure** | Compares the workload after the change with a counterfactual built from the 7 days before it, with a 90% confidence interval, confounder checks and health gates, and compares the result with the projection. |
| **Record** | Writes every outcome to an append-only, hash-chained ledger linked to the pull request, merge commit, synced revision and measurement. |

## Principles

<CardGrid>
  <Card title="Git is the only write path" icon="seti:git">
    No admission webhooks, no in-place mutation, no drift. Every change, including a rollback, is a pull request.
  </Card>
  <Card title="Projected is never realized" icon="warning">
    Projected, measured allocated and realized (billed) savings are labelled and never added together. Released capacity is never converted to money.
  </Card>
  <Card title="Fail closed, explain why" icon="error">
    When a change cannot be automated safely, GreenKube refuses and tells you why and what would fix it.
  </Card>
  <Card title="Evidence travels with the change" icon="document">
    The pull request carries the usage evidence, impact, risk, rendered diff and what will be verified after the merge.
  </Card>
</CardGrid>

## Who it is for

- **Platform and SRE teams** who run Argo CD or Flux and want optimization changes to go through the same review as any other change.
- **FinOps practitioners** who need measured savings, linked to commits, instead of a list of potential savings.
- **Sustainability teams** who want CO₂e next to cost on every change, with documented methods and limits.

It runs in the cluster it optimizes, **on-premises and on clouds** (AWS, GCP, Azure, OVHcloud, Scaleway, kubeadm, k3s, bare metal).

## What GreenKube does not do

- It never changes a workload directly in the cluster. Without GitOps, [manual mode](/concepts/gitops-delivery/#without-gitops-manual-mode) gives you the `kubectl` steps and measures the change once you mark it applied.
- It does not claim billed savings it has not measured. Today it measures **allocated** savings (what the changed workloads stop being charged) and shows the expected share that reaches the bill. Pool-level measurement of billed savings is on the roadmap.
- It recommends what it can deliver and measure: CPU and memory requests and limits (decreases and increases) and deletions of orphaned LoadBalancers and PersistentVolumes. Advisory-only analyzers (zombie pods, idle namespaces, off-peak scaling, node and NodePool advice) were removed in this release.
